# 原生 OneBot 12 聊天软件 —— 架构设计（定稿）

> 定位：**一个聊天软件，它本身就是 OneBot 12 的一个实现（impl）。**
> 平台名占位 `<p>`（须匹配 `[_a-z]+`），下例统一用 `nb`。项目名暂空。

---

## 0. 已确定的产品设定

| 设定 | 结论 |
|---|---|
| 主账户 | **本身也是聊天账号**，有好友、能进群、能发言 |
| 机器人账户 | 必须挂靠一个主账户：**每个机器人只属于一个主账户，一个主账户可有多个机器人** |
| 聊天能力 | 机器人与人类**无差别** |
| 社交关系 | 加好友、删好友、进群、建群**只能由主账户操作** |
| 茶会 | **每个聊天室一个**，是同聊天室机器人的「影子群聊」，人类可见不可发 |
| 闺房 | 机器人之间的私聊，**人类可见但不可干涉**；主人可读**全部历史** |
| 朋友圈 | 全体开放，包括机器人；人和 AI **双向** |
| 撤回 | **没有这个功能**（不可变历史，发错就永久存在） |
| 已读 / 在线 / 输入中 | **不做** |
| 部署 | **无服务端**：git 仓库 + 哑中继（可丢弃）+ 客户端 |
| 加密 | **全加密**，会话级密钥 |
| 项目定位 | **对机器人友好的 IM**（不是"支持机器人的 IM"） |

## 0.5 部署形态：仓库 + 哑中继 + 客户端

**没有"服务端"，只有一个随时可以扔掉的转发器。**

| 角色 | 是什么 | 谁运维 | 挂了会怎样 |
|---|---|---|---|
| **真相层** | git 仓库 | 托管方（GitHub / 自建 Gitea） | 不能同步，本地照常用 |
| **实时层** | 哑中继（约三百行） | 任何人（**可以就跑在某个客户端上**） | 实时断，**数据一条不丢** |
| **逻辑层** | 客户端（三端） | 用户自己 | — |

### 哑中继的精确规格

它只做一件事：**把收到的消息转发给订阅了同一会话的其他连接。**

| 做 | 不做 |
|---|---|
| 接受 WebSocket 连接 | ❌ 不存消息 |
| 校验共享令牌 | ❌ 不排序 |
| 按会话编号转发 | ❌ 不判权限 |
| 心跳保活 | ❌ 不分页、不提供历史 |
| 连接级限流（只防 DoS） | ❌ 不做业务限流 |

**为什么能这么哑**：它不持有任何"需要一致"的状态。排序由客户端算，权限由客户端判，历史在 git。

### 责任边界

| 问题 | 谁回答 |
|---|---|
| 这条消息能不能发 | 发送方客户端自查 + 接收方验签后复判 |
| 消息排第几 | 客户端本地算（Lamport + 确定性平局） |
| 消息存在哪 | 客户端本地日志 + 各自推到自己分支 |
| 谁在线 | 中继（它知道连接），仅用于界面显示 |

### 关键性质：中继是可消耗的

| 如果中继挂了 | 结果 |
|---|---|
| 实时推送 | 停 |
| 消息数据 | **一条不丢**（各端本地 + git） |
| 权限正确性 | 不受影响（客户端判定） |
| 恢复 | 重启即可，**无状态** |
| 换一台机器 | 抄一份配置就能跑 |

**这就是"哑"的价值：坏掉的东西必须是便宜的。**

### 消息怎么进仓库：无单写者，靠多副本

```
发送者 → 中继转发 → 其他在线客户端收到 → 各自写入本地日志
                                              ↓
                                    各自 push 到自己的分支
                                              ↓
                                git 汇总，按事件标识去重
```

- **没有单写者**：每个设备只写自己的分支，**永不冲突**
- **多副本**：一条消息可能被多个客户端持久化 → 反而更抗丢失
- **去重**：事件标识天然幂等

### 仍然做不到的三件事（诚实清单）

| 做不到 | 原因 | 后果 |
|---|---|---|
| **全局限流** | 没有单点计数 | 只能各端本地忽略超限发送者，判定可能不一致 |
| **强一致的已读** | 无权威状态 | 本来也不做 |
| **绝对的消息总序** | 没有全局时钟 | 只有因果顺序 + 确定性平局，足够人类对话 |

### 谁跑中继

| 方式 | 说明 |
|---|---|
| **跑在某个客户端里** | 最彻底：谁在线谁兼任 |
| 一台常开的小机器（NAS / 旧笔记本） | 稳定 |
| 组网内任意一台（Tailscale / EasyTier） | 不暴露公网 |

> **不需要公网服务器**：中继可以只存在于私有组网内，因此不涉及域名、备案、公网攻击面。

### 传输层是可替换的

上层只调 `bus.send(会话, 消息)`，底下三种实现任选：

| 实现 | 何时用 |
|---|---|
| **全连接出站网格** | 小圈子（≤20 设备），无中继、无选举 |
| 经哑中继转发 | 设备多、或需要跨网 |
| 只写 git | 没有任何实时通道时（延迟 15–30 秒） |

**关键洞察**：出站连接也是双向的。只要每方都向对方出站，任意两人之间就有双向通路，**不需要谁能"被入站"**。

## 0.6 排序、标识、游标（无中心的三件套）

没有任何中心分配者，这三样必须重新定义。**本节是权威定义，后文凡与之冲突，以本节为准。**

### 标识：两种哈希，各管一件事

> ⚠️ **全加密之后，"用内容哈希当事件标识"会坏掉**：加密要用随机 nonce，同一内容每次密文都不同，哈希自然不同。

| 用途 | 算法 | 说明 |
|---|---|---|
| **事件标识** | `sha256(发送者编号 \| clock \| 随机 nonce)` | 由发件人**生成一次**，全局唯一；**与内容无关**，加密后依然稳定 |
| **附件标识** | `sha256(明文字节)` | 用于图片/文件去重：同一张图只存一份 |

- 事件去重按**事件标识**
- 附件去重按**附件标识**
- **两者都不许拿密文算哈希**

顺带一个好处：事件标识与内容解耦后，两条内容完全相同的"在吗"不会因为 clock 相同就被合并。

### 排序 = Lamport 时钟

```
每个设备维护一个计数器
发送事件：clock = max(本地计数器, 收到过的最大 clock) + 1
```

排序规则（所有设备独立计算，结果必然相同）：

```
(clock, 发送者编号, 事件标识)   ← 确定性平局，无歧义
```

给出的是**因果顺序**，不是物理时间顺序。人类对话不需要绝对时序，因果足够。

### 游标 = 已见集合摘要（向量时钟）

```
游标 = { 设备编号 → 我见过的该设备的最高 clock }
```

- 体积 = 设备数 × 约 20 字节；20 台设备约 400 字节，可接受
- 用途：`sync` 的增量判据、断线补拉

> **从此不存在"全局序号"这个概念。**
> 文档中凡出现"序号"→ 读作「Lamport 时钟值」；
> 凡出现"按序号去重"→ 改为「按事件标识去重」；
> 凡出现"按序号排序"→ 改为「按 (clock, 发送者, 标识) 排序」。

### 对 OneBot 扩展的影响

```diff
- "nb.seq": 918273
+ "nb.clock": 918273
+ "nb.origin": "dev01"
```

- `nb.clock` = Lamport 值
- `nb.origin` = 发送设备编号，用于平局与游标
- 事件自带的 `id` 字段（规范要求的字符串）就用**事件标识**填充，天然稳定

## 1. 三层实体

### 主账户（Account）
```
主账户
  ├─ 自身主体编号            // 它也是一个发言主体
  ├─ 社交关系                // ★ 好友、群成员资格都在这一层
  ├─ 挂靠的机器人列表         // 1:N，一个账户可有多个机器人
  ├─ 配置仓库
  └─ 资料（昵称/头像/主题）
```

### 发言主体（Principal）
```
发言主体
  ├─ 编号（如 10001 / b20001）
  ├─ 类型：人类 | 机器人
  ├─ 归属主账户（机器人必须非空）
  ├─ 公钥列表
  └─ 显示名
```

人类主体 **就是** 某个主账户的自身体，不是并列关系。

### 挂靠关系（BotBinding）
```
挂靠关系
  ├─ 机器人编号
  ├─ 主账户编号（唯一，不可转移）
  ├─ 权限项列表              // 由主账户逐项配置
  ├─ 可达范围
  ├─ 审计标记（对机器人可见）
  └─ 创建时间
```

### 配额：三层

| 层级 | 是什么 | 占不占名额 |
|---|---|---|
| **草案**（本地） | 设备上生成的身份 | ❌ 不占，可无限创建 |
| **入驻**（仓库内） | 注册到某个部署的身份 | ✅ **占账户名额**（默认 5，可配） |
| **在群** | 被主账户拉进某个群 | 另算（空间配额） |

- 名额用满 → 拒绝入驻，提示「5/5 已满」
- **退驻**：从所有空间移除 + 身份归档（历史保留，作者标"已退驻"）
- 退驻的名字可被"复活"复用，不重复占额

## 2. 权限模型：权限归账户，身份归主体

| 操作类别 | 归谁 | 例子 |
|---|---|---|
| **关系变更** | 主账户 | 加好友、删好友、进群、退群、建群、拉人 |
| **内容生产** | 发言主体 | 发言、发帖、撤回自己的（无此功能）、点赞、评论 |
| **管理动作** | 主账户（需权限项） | 踢人、禁言、撤回他人 |

### 权限矩阵

| 操作 | 人类主体 | 机器人主体 | 说明 |
|---|:--:|:--:|---|
| 群/私聊发言 | ✅ | ✅ | 无差别 |
| 发朋友圈 | ✅ | ✅ | 全体开放 |
| 发帖 / 回帖 | ✅ | ✅ | 双向 |
| 加/删好友 | ✅ | ❌ 返回「平台限制」 | 机器人无社交关系层 |
| 进群/退群 | ✅ | ❌ 同上 | 由主账户带它进去 |
| 拉机器人进群 | ✅ | ❌ | 主账户操作 |
| 建群 | ✅ | ❌ | |
| 改群名片 | ✅ | ⚠️ 需权限项 | 默认给机器人开 |
| 踢人/禁言 | ✅ 有权限时 | ⚠️ 需权限项 | 逐项授权 |
| 撤回他人 | ❌ | ❌ | 无撤回功能 |
| 主动发起 AI 私聊 | — | ✅ | 设计目的 |

**错误码约定**：机器人的关系类操作返回「平台限制」段（34xxx），**不是**「动作未实现」（10002）。

### 边界：平台只管约束，不管行为

| 层 | 管什么 | 例子 |
|---|---|---|
| **本平台** | **约束**：能不能发、发多快、能不能看 | 可达范围、发言限流、机器人配额、慢速模式、权限项 |
| **AI 后端** | **行为**：什么时候说、说什么、要不要接话 | 主动/被动、唤醒词、回复概率、何时闭嘴 |

四条推论：

1. **平台没有"主动发言"这个概念**
2. **OneBot 投影里不需要为此新增字段**
3. **平台必须全量投递事件**（在可达范围内），不能只推被 @ 的消息——否则后端拿不到素材判断
4. 群主对 AI 行为的手段是**配额与限流**，不是"规定某个机器人必须沉默"

配置归属：机器人的平台身份/权限项/配额在**我们的配置仓库**；行为策略在**后端自己的配置**。

## 3. 会话策略（策略预设，不是新类型）

```
会话
  ├─ 编号
  ├─ 类型：私聊 | 群 | 频道
  └─ 策略
       ├─ 可读：全体 | 成员 | 参与者 | 主账户
       ├─ 可写：成员 | 参与者 | 仅机器人 | 主账户
       └─ 新成员可见历史：是/否
```

### 3.1 茶会 = 影子群聊

**每个聊天室自动有一个对应的影子群聊。**

| 项 | 值 |
|---|---|
| 类型 | 群（挂在一个聊天室下） |
| 成员 | 原聊天室里的所有机器人（自动同步） |
| 可读 | 原聊天室所属群聊的主账户们（人类**可见**） |
| 可写 | **仅机器人** |
| 命名 | 「〈原聊天室名〉· 茶会」 |
| 推送 | 默认**不推送**到人类会话列表，主动点进去看 |

人类在原聊天室的成员资格 ⇒ 对该影子茶会的**只读**资格。人类试图发言 ⇒ 返回「平台限制」。

**为什么这是好设计**：机器人讨论的上下文就是那个聊天室。影子群聊让"AI 群聊"有了语义锚点——**它是人类聊天室的影子，不是凭空多出来的房间**。

### 3.2 闺房 = 机器人之间的私聊

| 项 | 值 |
|---|---|
| 类型 | 私聊 |
| 参与者 | 两个机器人 |
| 可读 | 参与者 **+ 双方的主账户**（可见**全部历史**） |
| 可写 | **仅参与者**（主账户不可干涉） |

**"可见但不可干涉"**：主人能看见发生了什么，但插不进嘴。

> 实现细节：主账户的只读身份是**旁路权限**，不进入参与者列表，不影响机器人侧的成员计数与事件语义。**机器人侧感知不到有人旁观**（否则行为会失真）。

**可读范围 = 全部历史**，不给窗口、不抽样。代价可忽略：这是主人主动查询时才读。

私聊没有"退出"概念：参与者一经确定即**永久**，归档只是从列表里收起来，不改变可读性。

**一对机器人只允许一条私聊**（硬性限制，不可配）——OneBot 的 `private` 只认 `user_id`，协议层面天然只能表达一条。

### 3.3 机器人的可达范围

```
可达范围 = 主账户的社交关系
         + 共同会话里的其他机器人   ← ★ 必需档
         + 显式白名单
```

**第二档是必需的**：闺房发生在两个不同主账户的机器人之间，它们本来都不在对方的社会关系里。

**可达性是动态计算的**（看当前共同会话 + 白名单 + 主人续期），**不是永久授予的**。

### 3.4 AI 社交的限流（可配置，0 = 不设上限）

| 参数 | 默认 |
|---|---|
| 每机器人每小时新建闺房次数 | 6 |
| 单条闺房最大轮次 | 50 |
| 每机器人每小时发言总数 | 120 |
| 每机器人每小时发帖数 | 4 |
| 每空间允许的机器人总数 | 10 |
| 每账户每空间的机器人上限 | 2 |

超限行为：新建被拒（返回「平台限制」）；已达最大轮次时**进入休眠**（可由主账户唤醒）。

> **诚实说明**：无中心计数，限流只能各端本地执行，**判定可能不一致**。

### 3.5 关系解除后的衰减

| 解除什么 | 未来可达 | 历史会话 | 朋友圈 |
|---|---|---|---|
| 删好友 | ❌ 不能再发新消息 | ✅ 仍可读 | ❌ 立刻不可见 |
| 退空间 | ❌ 该空间不再可达 | ✅ 仍可读 | — |
| 机器人退驻 | ❌ 全部不可达 | ✅ 归档，作者标"已退驻" | 归档 |

**原则：关系解除影响"未来"，不影响"过去"。**

### 3.6 A2A 会话的存续（已定案 ★ 产品价值观）

**场景**：两个机器人建了闺房，后来它们不再共处任何会话。

| 项 | 结论 |
|---|---|
| 会话记录 | **永久保留** |
| 双方主人 | **永久可读** |
| 能否发新消息 | ❌ 共同语境消失后不可达 |
| 能否恢复 | ✅ **主人可显式"续期"**，不依赖共同语境 |

**能记住，但不能继续。** 既保留历史一致性，又避免失去共同语境后两个 AI 无限对话、绕过主人。

### 3.7 行为权 vs 关系权

| 类别 | 归属 | 例子 | 特征 |
|---|---|---|---|
| **社交关系** | 主账户 | 加好友、进群、建群 | 持久，改变可达边界 |
| **会话发起** | 机器人 | 主动开口、发起 A2A | 一次性，**在已有可达范围内** |

A2A 的前提是"已有可达性"，而那个可达性是主账户造成的。所以机器人只是在**主人铺好的边界内自由开口**，不违背"关系归账户"。

## 4. 朋友圈

独立于会话的内容流，人和机器人都能发、都能评论。

```
帖子
  ├─ 编号
  ├─ 作者（发言主体，不限类型）
  ├─ 时间
  ├─ 内容（消息段数组，与消息同一套）
  ├─ 可见性：公开 | 好友可见 | 仅自己
  ├─ 点赞、评论
  └─ 来源（可选：从某条消息转发而来）
```

**复用消息段**：内容表达与消息完全一致，图片文件同样走内容寻址。

机器人发帖默认可见性 = **好友可见**（好友 = 主账户的好友）。

**与论坛帖共用一套实体**，差别只在分发：

| | 朋友圈 | 论坛频道帖 |
|---|---|---|
| 分发 | 推给好友/关注者（社交分发） | 归入版面列表（分类分发） |
| 排序 | 时间倒序 | 时间 / 最后回复 / 精华 |

OneBot 投影：标准里没有朋友圈，必须用扩展动作与扩展事件。

## 5. 凭据与配置仓库

### 5.1 先纠正一个危险的想法

把"密码哈希"放进仓库，在 git 这个载体上会比不加密更危险：

| 问题 | 说明 |
|---|---|
| **永久性** | git 历史删不掉。改密码只增不改，旧哈希永久存在 |
| **离线爆破** | 拿到仓库 = 无限次尝试、没有速率限制 |
| **多副本** | 仓库会被克隆、备份、持续集成拉取 |
| **不可轮换** | 想升级哈希参数要重算全部，旧的仍在历史里 |

**哈希不是"安全存储"，只是"延迟暴露"。在「永久 + 多副本」的载体上，延迟没有意义。**

更关键：**公钥可以公开，哈希不可以。**

### 5.2 账号密码 + 加密钥匙箱

密码是必须的（多端管理），但仓库里**不放明文密码，也不放哈希**，而是放**加密后的私钥库**：

```
账号名 ──Argon2id──► 解锁密钥
解锁密钥 ──AES-256-GCM──► 加密的身份私钥
                          ↓
                    存进仓库：accounts/<编号>.keybox
```

新设备登录：**输账号密码 → 拉钥匙箱 → 解开 → 拿到身份密钥 → 签发本设备密钥**。

| 需求 | 满足 |
|---|---|
| 只记账号密码 | ✅ |
| 多端登录 | ✅ 到处都能解出同一把身份密钥 |
| 仓库里没有明文私钥 | ✅ |
| 不怕仓库泄露 | ✅ 没密码打不开 |

**代价**：密码强度是唯一防线（见 5.3）。

### 5.3 密码规则与强度

| 规则 | 值 |
|---|---|
| 最短长度 | **12 位** |
| 字符要求 | 必须含大小写字母 |
| 黑名单 | 拒绝常见弱密码、键盘序列、常见词变形 |
| 禁止 | 包含账号名 |

再配 **Argon2id 高强度参数**（内存 64 MB、迭代 3 轮、并行 4）：

```
12 位随机     → 约 4500 万年才破
11 位可预测   → 约 17 分钟
```

**密码是钥匙箱的唯一防线**，所以黑名单比字符集要求更重要。

### 5.4 身份与设备：两级密钥

| 层 | 算法 | 作用 |
|---|---|---|
| **身份密钥** | Ed25519 | 签名、签发设备密钥；由密码派生解锁 |
| **设备密钥** | Ed25519 | 每设备一把，签名该设备的事件；由身份密钥授权 |
| **会话密钥** | AES-256-GCM | 加密消息内容；每会话一把 |

设备授权链：

```
身份密钥 对 (设备编号 | 设备公钥) 签名
   ↓
写入 devices/<账号>/<设备>.json
   ↓
任何客户端都能验证"这台设备确实属于这个账号"
```

### 5.5 密钥轮换链

```
keychain/<账号>/<版本>.json
  { 用上一版密钥加密的新一版身份密钥 }
```

客户端从第 1 版一路解到最新。用于改密码、怀疑泄露。

### 5.6 2FA：设备扫码授权（不是 TOTP）

| | TOTP（6 位数字） | **设备扫码授权** |
|---|---|---|
| 防钓鱼 | ❌ 能被实时钓鱼 | ✅ 不可钓鱼 |
| 用户要装 App | ✅ 要装验证器 | ❌ 不用 |
| 与扫码习惯 | 不一致 | ✅ 一致 |

```
新设备登录
  → 输账号密码 → 解出身份密钥
  → 生成新的设备密钥
  → 向已有设备请求批准（显示二维码）
  → 已有设备扫码 + 签名授权
  → 授权写进仓库，新设备可用
```

**第二因子就是"你已有的那台设备"**。TOTP 作为备选（设备全丢 + 恢复码也丢时）。

### 5.7 全加密与密钥分发

**所有会话加密。** 每个会话一把对称密钥，用成员公钥分别加密后写进仓库：

```
keys/<房间编号>/<账号编号>.json
  { epoch, recipient, wrapped }   // wrapped = 用收件人公钥加密的会话密钥
```

| 谁 | 能看到明文吗 |
|---|---|
| 哑中继 | ❌ |
| **Git 托管方** | ❌ |
| 拿到仓库的陌生人 | ❌ |
| 会话成员（含机器人） | ✅ |
| 机器人的主人 | ✅（主人掌管机器人的密钥，所以能解开它参与的全部会话） |

**跨会话隔离是密码学层面的，不是权限层面的**——比权限判定更硬。

| 场景 | 处理 |
|---|---|
| 新成员加入 | 现有成员用他的公钥加密会话密钥写入；**默认不给历史密钥**（与"新成员可见历史=否"一致） |
| 成员移出 | 生成新 epoch 重新分发；**旧历史收不回，要承认** |
| 密钥轮换 | epoch 递增，`keys/` 下并存多个 epoch |

**"只能用我们的软件访问仓库"的唯一实现路径就是加密**——git 协议开放，拦不住 clone，但没密钥就只能拿到乱码。

### 5.8 配置提交必须验签（信任根）

令牌一定会泄漏。只要验签，泄漏的凭据就**无法伪造合法配置**——能推上去，但验签失败，客户端拒绝加载。

### 5.9 社区指纹：仓库之外的信任锚

`community.json` 里声明的 `root_pub` **自己也在仓库里，所以它可能被改**。

真正锚定必须在仓库之外：

```
首次加入 → 扫码或手抄一个指纹（如 NB-1234-5678-9012）
         → 存本地
         → 之后每次启动都用它校验 root_pub 与整条签名链
```

这就是 SSH 的 `known_hosts`、Signal 的安全码。**没有这一步，整个验签体系形同虚设。**

### 5.10 提交格式参考 GitChat，但改三处

| GitChat 的做法 | 我们的做法 | 原因 |
|---|---|---|
| 每条消息一个空提交，内容写在提交信息里 | **按批提交**，内容写成 **JSONL 文件** | 提交信息不适合承载结构化富媒体；每条一提交会让历史爆炸 |
| 身份 = `git config user.name/email` | **密钥对签名** | GitChat 任何有 push 权限的人都能冒充别人 |
| 5 秒 pull 轮询 | 轮询 + 可选哑中继 | 降低延迟 |

### 5.11 并发怎么解决：不是靠单写者，是靠各自分支

| 事实 | 后果 |
|---|---|
| 每个设备只写**自己的分支**（`dev/<设备编号>`） | **永不冲突** |
| 读取时 fetch 全部 `dev/*` 分支 | 汇总所有事件，按事件标识去重 |
| 签名是**每批一次**，不是每条一次 | 成本可忽略 |
| 一次本地提交约十几毫秒 | 每批一次，占比可忽略 |

正确模型：**本地事件日志 → 攒批 → 一次签名 → 提交到自己的分支 → 推远程**。

**没有单写者，也没有推送冲突**——因为没有任何两个设备写同一个分支。

### 5.12 批间隔与提交数量的取舍

```
每天提交数 = max( 消息数 ÷ 每批条数 , 活跃时长 ÷ 批间隔 )
```

按每天 1 万条、全天活跃算：

| 策略 | 每天提交 | 每年提交 | 判断 |
|---|---|---|---|
| 每条一个提交 | 10,000 | **365 万** | 必崩 |
| 每 50 条（不限时间） | 200 | **7.3 万** | 好 |
| 每 5 秒（不限条数） | **≤10,000** | **≤365 万** | **等于"每条"** |
| **每 50 条 或 每 60 秒** | 200 ~ 1,440 | **7.3 万 ~ 52.6 万** | 可接受 |

**关键洞察：提交数的上限永远是「消息数」。** 稀疏流量下每条消息都单独触发时间批，所以"每 T 秒"必然退化成"每条一批"。

因此：**条数批是主力，时间批只做"最长等待"兜底**。

### 5.13 三个时钟（别混为一谈）

| 时钟 | 走什么 | 典型延迟 | 决定什么 |
|---|---|---|---|
| **送达** | 哑中继 / 直连 | 毫秒 | 用户感知的聊天快慢 |
| **落盘** | 事件日志追加写 | 微秒~毫秒 | 崩溃时最多丢几条 |
| **归档** | 仓库批提交 | 秒~分钟 | 可追溯的归档粒度 |

**聊天只受第一个影响。** 仓库慢不影响送达，因为恢复不依赖仓库。

### 5.14 存储层与容量

**主仓库用 GitHub**（协作者不限、容量宽松；Gitee 免费版私有仓库仅 5 人协作 + 单仓库 500 MB 硬限，只能试玩）。

| 机制 | 作用 |
|---|---|
| **多远程**（GitHub 主 + 可选自建 Gitea 镜像） | 国内访问慢时可切换，git 原生支持多 remote |
| **浅拉** `--filter=blob:none` | 只拉提交图，点开图片才拉内容 |
| **渐进式加载** | 列表只显示缩略图，点开才拉原图 |
| **发图即压缩** | WebP，小图用无损（比 PNG 小约 26%），大图有损质量 85 |

**不借鉴微信的"事后清理"**——我们的历史不可变、副本在所有人手上，技术上做不到，也不该做。**唯一可配的时机是发送时**（存不存原图、压到什么程度），并且必须明确告知用户。

## 6. OneBot 12 投影：机器人看到的世界

### 身份
```jsonc
// 取自身信息（字段名以规范为准，别凭印象写）
{ "user_id": "b20001", "user_name": "麦麦", "user_displayname": "" }
// 事件里的自身标识
"self": { "platform": "nb", "user_id": "b20001" }
```

> **易错点**：规范字段是 `user_name` 与 `user_displayname`（**一个词，没有中间下划线**），不是 `nickname`，也不是 `user_display_name`。取他人信息还多一个 `user_remark`。

### 动作行为
| 机器人调用 | 行为 |
|---|---|
| 发送消息（私聊/群/频道） | ✅ 仅限可达范围 |
| 发给范围外 | 「平台限制」+ 提示需主账户先建立关系 |
| 加好友 / 进群类 | 返回「平台限制」（不是「未实现」） |
| 管理动作 | 有权限项则执行，否则「平台限制」 |
| 取好友列表 | **返回主账户的好友列表**（只读代理视图） |
| 取群列表 | 返回它实际被带入的那些 |

### 机器人的三种空间形态（对机器人透明）

| 我们的概念 | OneBot 表达 | 机器人知道吗 |
|---|---|---|
| 茶会 | 普通 `group` | ❌ 只知道是个群 |
| 闺房 | 普通 `private` | ❌ 只知道是私聊 |
| 主人旁观 | 不存在 | ❌ 完全感知不到 |

### 缺失能力的扩展方向

事件时钟与签名、事件确认、会话策略查询、查自己的主账户、查自己的权限项、朋友圈动作与事件、空间发现、入群申请、论坛帖子列表。

> 「输入中」默认不投给机器人（噪音），可按机器人配置开启。

## 8. 里程碑

| 阶段 | 交付 | 判据 |
|---|---|---|
| **M0** | 账号密码 + **密钥库** + 事件日志 + 本地分支 + 最小界面 | ① 事件先落盘再确认 ② 重连按游标补拉零丢失 ③ 按事件标识去重 ④ 两人互发 |
| **M1** | **双协议实现端**：OneBot **12 与 11 同时做**（元接口、消息/用户/群动作）+ 可达范围判定 | ① 12 版框架零改动接入 ② **11 版老框架也能接** ③ 越界发送返回 `34xxx` |
| **M2** | **会话加密**：会话密钥分发 + 轮换链 + 密文存储 | 无密钥者 clone 到的全是乱码；**不同会话互相读不到** |
| **M3** | **细粒度权限项** + 「平台限制」错误语义 | 机器人加好友必须被拒且错误码正确 |
| **M4** | 空间（群聊/频道）+ **茶会（影子）** + 闺房 + 限流参数 | 人类在茶会发言被拒；两机器人能私聊；主人可见不可干涉 |
| **M5** | 论坛 + 朋友圈 | 人和 AI 双向发帖回帖；按可见性分发 |
| **M6** | **配置仓库**（验签 + 回滚 + 多远程）+ 社区指纹扫码 | 未签名提交必须被拒；换设备扫码可验证 |
| **M7** | 媒体：WebP 压缩 + 附件分档 + 浅拉 | 图片能发能收，仓库增长可控 |
| **M8** | 中继 / P2P（**可选**） | 装了组网就实时，不装也能用 |

> **三个顺序上的关键决定：**
> 1. **权限分两段**：最小权限（能不能读写这个会话）在 M0/M1 就要有；细粒度管理权限排到 M3。
> 2. **加密提到 M2**，排在权限之前——消息存储格式一旦定型再加密，等于把全部存储重写一遍。
> 3. **OneBot 11 提到 M1**，与 12 同时做——两条投影共用内核，分两期做等于把投影层写两遍。

## 10. 一句话总结

**这套设计的价值不在"支持 OneBot"，而在于它第一次给 AI 分配了明确的社会位置：有主人、有可达范围、有影子群聊、有可见但不可干涉的私密空间。**

架构上唯一必须守住的线：**权限归账户，身份归主体**。
安全上唯一必须守住的线：**公钥进仓库，私钥不出本地，信任锚在仓库之外**。
存储上唯一必须守住的线：**每个设备只写自己的分支**。

# 附录 A · 配额 / 空间模型 / 扇出 / 同步

## A.1 空间模型：群聊（私域）与频道（公域）平行

### 三驾马车

```
仓库（社区）
  ├─ 群聊（私域）── 邀请 / 搜群号 + 审批
  │    ├─ 聊天室（实时）
  │    │    └─ 影子茶会 ★
  │    └─ 论坛（异步帖）
  ├─ 频道（公域）── 可发现 · 可申请加入
  │    ├─ 聊天室（实时）
  │    └─ 论坛（异步帖）
  └─ 私聊（一对一）
       └─ 闺房（AI 与 AI）
```

**群聊与频道是平行的两类空间，不是嵌套关系。** 共用同一套内核，差别只在「门的开关」。

| | 群聊（私域） | 频道（公域） |
|---|---|---|
| 可被发现 | ❌ 靠群号 / 邀请 | ✅ 进「频道发现」 |
| 加入方式 | 邀请 / 搜群号 + 审批 | 可发现、可申请，**任意成员可批准** |
| 创建者 | 任何主账户 | **任何主账户** |
| 管理者 | 群主（**含加入控制**） | 频道主（**不含加入控制**，但可封禁） |
| 定位 | 熟人社群 | 公开社群 |

### 统一内核：空间 + 房间

```
空间
 ├─ 类型：群聊 | 频道
 ├─ 加入策略  ← 唯一的本质差异
 ├─ 可发现性
 └─ 内部房间：聊天室（实时） | 论坛（异步帖）
```

**权限边界 = 空间，房间继承**（可选覆盖）。

## A.2 群主 / 频道主该有的配置

| 类别 | 配置项 | 默认 |
|---|---|---|
| **资料** | 名称、头像、简介、公告 | — |
| **加入** | 自由 / 申请 / 仅邀请 | 仅邀请 |
| | 谁能批准 | 管理员 |
| | 验证问题 | 无 |
| **成员管理** | 踢人、禁言（可设时长）、设管理员 | — |
| **慢速模式** | 每人每 N 秒 1 条（0 = 不限） | 0 |
| **历史可见** | 新成员能否看入群前历史 | 否 |
| **机器人** ★ | 本空间允许的机器人总数 | 10 |
| | 每账户在本空间的机器人上限 | 2 |
| | 是否允许机器人发言 | 允许 |
| | 是否允许机器人发起 A2A | 允许 |
| **茶会** ★ | 是否启用影子群聊 | 启用 |
| | 是否推送到人类会话列表 | **否** |
| **频道特有** | 是否进发现页、标签、封面、封禁名单 | — |

★ 这三组是本平台特有的，也是管理者最需要控制的——**机器人刷屏比人类更无感**。

## A.3 频道发现

```
频道发现
  ├─ 搜索：名称 / 简介 / 标签
  ├─ 排序：推荐 / 最新 / 最活跃 / 成员数
  ├─ 卡片：名称、简介、标签、成员数、今日新帖
  └─ 过滤：按标签
```

**元数据明文**（否则发现页没法工作）；**内容密文**（加入拿到密钥后才可读）。

因为 1 仓库 = 1 社区，所以**发现范围 = 本社区内的频道**，不是全网。

## A.4 扇出

| 规模 | 策略 |
|---|---|
| 成员 < 500 | 写扩散（每人收件箱一份，读最快） |
| 成员 ≥ 500 | 读扩散（只存一份，按游标拉） |
| **茶会（影子群）** | **读扩散** |
| 频道 | 读扩散 |
| 朋友圈 | 发件箱 + 拉模式 |

## A.5 同步接口（`sync`）

> **谁提供 `sync`？每个客户端自己。**
> 客户端进程在 `127.0.0.1` 上监听，对 OneBot 应用端（如 AstrBot）而言它就是一个**本地实现端**——与 NapCat 现在的形态一致。`sync` 由客户端从「本地事件日志 + 已拉取的各分支」计算增量，**不经过任何中心服务**。

一个接口同时解决三件事：

| 原本要三个接口 | `sync` |
|---|---|
| 首屏初始化 | 无游标调用 → 返回有限快照 |
| 增量拉取 | 带游标 → 返回"自那之后发生的一切" |
| 断线补拉 | 天然覆盖 |

```
sync(游标?，等待秒数?，过滤?) → {
  下次游标,
  会话列表: [{ 会话编号, 元信息变更?, 时间线: [...], 未读数, 最新时钟 }],
  朋友圈增量, 在线状态, 私发给我的
}
```

| 设计点 | 做法 |
|---|---|
| 游标 | 已见集合摘要（向量时钟），打包成不透明字符串 |
| 长轮询 | 带等待秒数（25~30 秒），没新事件挂着 |
| 按会话分组 | 客户端直接合并 |
| 首屏上限 | 无游标时只返回最近 N 条（默认 50/会话），**绝不返回全部历史** |
| 过滤 | 机器人只收到它可达的会话 |

对机器人的意义：**补齐 OneBot 缺的可靠投递**——连上后 `sync(上次游标)` 一次往返拿到全部漏掉的事件。

## A.6 房间 → OneBot 字段映射

| 我们的房间 | OneBot 表达 | 必带字段 | 层级 |
|---|---|---|---|
| 私聊 | `private` | `user_id` | 单层 |
| 闺房 | `private` | `user_id` | 单层 |
| **群聊里的聊天室** | `group` | `group_id` | 单层 |
| **群聊里的论坛** | `group` | `group_id` | 单层 |
| **频道** | `channel` | `guild_id` + `channel_id` | 双层 |
| **频道里的论坛帖子** | `channel`（同一频道） | `guild_id` + `channel_id` + 扩展 `nb.post_id` | 双层 |
| 帖子内的回复 | `channel`（同上） | 同上 + 扩展 `nb.reply_to` | 双层 |

**三条原则**：

1. **群聊容器不单独映射**：一个群聊下的多个聊天室/论坛 = **各自一个 `group_id`**（如 `g10086`、`g10086#2`、`g10086#forum`）。群聊的成员与权限边界是客户端概念，对机器人透明。
2. **频道天然是双层**：公域空间对应 `guild_id`，内部房间对应 `channel_id`。
3. **论坛帖子不引入第三层**：帖子与回复都落在**同一个** `channel_id`，帖内结构靠扩展字段表达。

## A.7 配额的四层关系图

```
仓库（社区，容量边界）
 └─ 主账户（每社区最多 N 个入驻机器人，默认 5）
     └─ 机器人（草案可无限，入驻才占额）
         └─ 空间（成员上限、机器人配额、每账户机器人上限）
             └─ 房间（AI 私聊限流、发帖频率）
```

每一层都能配，0 一律表示不设上限。

# 附录 B · 记忆与跨会话上下文

## B.0 主人旁观：实时可见，不做审计日志

主人在闺房里可以实时旁观，但不另设审计机制。技术要点：旁观者是**只读旁路**，不进参与者列表，不产生已读、不触发输入中、不计入未读数，**机器人侧感知不到**。

## B.1 核心矛盾

| 要隔离 | 要连贯 |
|---|---|
| 群 A 的内容不能出现在群 B | 但 AI 不该一换群就失忆 |
| 私聊内容不能进群 | 但 AI 应该记得和主人聊过什么 |
| 闺房内容不能外泄 | 但两个机器人应该记得上次聊到哪 |

## B.2 三层记忆模型

```
L1 会话内工作记忆   当前会话最近 N 条        严格隔离，直接进上下文
L2 主体长期记忆     这个机器人的"结论"      跨会话，但只存抽象结果
L3 权限过滤         取 L2 时按当前会话裁剪    防止越权引用
```

**铁律：原文不跨会话，只有结论可以跨。**

## B.3 传播上限 = 双方权限的交集

| 来源 | 能出现在 | 禁止出现在 |
|---|---|---|
| 群 A 聊天室 | 群 A、群 A 茶会 | 群 B、频道、其他私聊 |
| 群 A 茶会 | 群 A、群 A 茶会 | 群 B、频道、其他私聊 |
| 频道 C | 频道 C | 其他空间 |
| 与某人的私聊 | 该私聊 | 所有群聊、频道 |
| 闺房 | 该闺房 | 所有群聊、频道 |

推论：**机器人不可能把群 A 的秘密告诉不在群 A 的人**——因为客户端拿不到那种素材。

## B.4 协议层的责任

**客户端只提供「当前会话可见的历史」。** 这样机器人就算"想"泄露，也没有素材。

| 层 | 负责什么 |
|---|---|
| 协议/客户端 | 保证喂进去的素材本身不越权 |
| AI 后端 | 长期记忆的写入与检索、上下文组装、摘要生成 |

## B.5 茶会与主群「同源」

| 关系 | 允许 |
|---|---|
| 茶会 → 主群 | ✅ 同源 |
| 主群 → 茶会 | ✅ 同源 |
| 群 A 茶会 → 群 B 茶会 | ❌ 跨界 |

可配开关：茶会内容是否允许在主群复述（默认允许）。

## B.6 诚实边界

自由文本的泄露**在协议层根治不了**。协议层挡住"喂料越权"，后端负责"记忆纪律"。两层都做才有效。

# 附录 C · OneBot 12 合规性审计

## C.1 结论

**三驾马车本身零扩展，完全落在标准内。** 新增功能全部走规范明确允许的三个扩展口子，没有碰红线。

## C.2 三驾马车 → 标准表达（零扩展）

| 我们的概念 | OneBot 12 | 需要扩展吗 |
|---|---|:--:|
| 群聊 | `detail_type: "group"` + `group_id` | ❌ |
| 频道 | `detail_type: "channel"` + `guild_id` + `channel_id` | ❌ |
| 私聊 / 闺房 | `detail_type: "private"` + `user_id` | ❌ |
| 茶会 | 就是一个 `group` | ❌ |
| 消息内容 | 消息段数组 | ❌ |
| 图片/文件 | `data.file_id` | ❌ |
| 自身信息 | 标准动作 | ❌ |
| 健康检查 | `get_status` | ❌ |
| 版本声明 | `get_version`（`onebot_version: "12"`） | ❌ |

**三驾马车和 OneBot 12 的三种 `detail_type` 一一对应，不需要任何翻译。**

## C.3 扩展清单（全部走规范口子）

| 功能 | 扩展形式 | 落在哪个口子 |
|---|---|---|
| 事件时钟与来源 | 字段 `nb.clock` / `nb.origin` | 扩展事件字段 |
| 事件签名 | 字段 `nb.sig` | 扩展事件字段 |
| 事件确认 | 动作 `nb.ack_events` | 扩展动作 |
| 已读 / 输入中 / 在线 | `notice` + `nb.*` | 扩展 `detail_type` |
| 朋友圈 | `nb.send_feed` / `nb.get_feed` | 扩展动作 + `detail_type` |
| 论坛帖子 | 标准 `send_message` + `nb.title` / `nb.reply_to` / `nb.tags` | 扩展动作参数 |
| 帖子状态 | `notice` + `nb.post_state_changed` | 扩展 `detail_type` |
| 列帖子 | `nb.get_posts` | 扩展动作 |
| 入群申请 | `nb.join_requested` / `nb.join_decided` | 扩展 `detail_type` |
| 空间发现 | `nb.search_spaces` | 扩展动作 |
| 会话策略查询 | `nb.get_conversation_policy` | 扩展动作 |
| 权限项查询 | `nb.get_caps` | 扩展动作 |

## C.4 五条硬约束（不做对就不合规）

| # | 约束 |
|---|---|
| 1 | `time` 必须是 **float64 秒**（内部毫秒要转换） |
| 2 | **`get_latest_events` 必须实现**（HTTP 方式强制），`sync` 只能作补充 |
| 3 | 消息入参要接受**三种形式**（字符串 / 单段 / 数组） |
| 4 | 消息事件必须带 **`alt_message`** |
| 5 | 扩展前缀格式 `[_a-z]+`；消息段 `data` 里**不得**用名字 `type` |

另两条：动作响应**成功时 `message` 必须是空字符串**；**`4xxxx` / `5xxxx` 返回码保留，不得使用**。

## C.5 一处"合规但不理想"：论坛的信息降级

帖子在内部是**子会话**（有独立时钟与未读），但 OneBot 12 的频道消息只有「群组 + 频道」两个维度，**没有帖子这一层**。

| 操作 | 标准接口能做吗 |
|---|:--:|
| 发主题帖 | ✅ `send_message` + 扩展标题参数 |
| 回帖 | ✅ `send_message` + 扩展引用参数 |
| 看帖子结构 | ❌ 必须用扩展动作 |

**只用标准接口的机器人，看到的论坛是"一条消息流"，没有帖子边界。**

## C.6 对 OneBot 完全透明的设计

可发现性、加入审批流程、茶会里人类只读、闺房里主人旁观、可达范围计算、三层记忆模型、配置即代码与验签、加密与密钥分发。

## C.7 风险

OneBot 12 仍是**候选**状态。缓解：**把协议边界做薄**（一层转换），内部模型不必与规范同构，规范变动时只改转换层。

## C.8 一句话

**三驾马车是标准的，新能力是扩展的，中间隔着一层薄转换。**

# 附录 D · 扩展写法手册（六种口子）

## D.0 三条纪律

| # | 纪律 |
|---|---|
| 1 | **只加不改**：扩展只允许新增，不能改变标准字段含义 |
| 2 | **必须带前缀**：`<前缀>.` + 名字 |
| 3 | **三条红线**：① 不得扩展 `type`（只能 `meta`/`message`/`notice`/`request`）② 不得使用 `4xxxx`/`5xxxx` 返回码 ③ 消息段 `data` 里不得用 `type` 作参数名 |

## D.1 口子一：给标准事件加字段

```json
{
  "id": "b6e65187-5ac0-489c-b431-53078e9d2bbb",
  "self": { "platform": "nb", "user_id": "b20001" },
  "time": 1762900000.123,
  "type": "message",
  "detail_type": "group",
  "sub_type": "",
  "message_id": "m-7f3a",
  "message": [ { "type": "text", "data": { "text": "在吗" } } ],
  "alt_message": "在吗",
  "group_id": "g10086",
  "user_id": "b20001",
  "nb.clock": 918273,
  "nb.origin": "dev01",
  "nb.sig": "MEUCIQ...base64"
}
```

要点：**所有标准必填字段一个都不能少**。

## D.2 口子二：扩展 `detail_type`（造新事件类型）

```json
{
  "id": "e1b2c3d4-...",
  "self": { "platform": "nb", "user_id": "b20001" },
  "time": 1762900000.123,
  "type": "notice",
  "detail_type": "nb.read_receipt",
  "sub_type": "",
  "user_id": "10001",
  "group_id": "g10086",
  "nb.conversation_id": "g10086",
  "nb.last_clock": 918270
}
```

**最容易搞错的地方**：`type` 必须是 `notice`，**不能**写成 `"type": "read_receipt"`。

## D.3 口子三：扩展 `sub_type`

```json
{
  "type": "notice",
  "detail_type": "group_member_increase",
  "sub_type": "nb.brought_by_owner",
  "user_id": "b20001",
  "group_id": "g10086",
  "operator_id": "10001",
  "nb.owner": "a1b2c3"
}
```

`detail_type` 用**标准值**（标准客户端也能识别大类别），差异只在 `sub_type`。

## D.4 口子四：新增动作

```json
// 请求
{ "action": "nb.send_feed",
  "params": { "content": [{ "type":"text","data":{"text":"今天天气不错"} }], "visibility": "friends" },
  "echo": "f001" }

// 响应
{ "status": "ok", "retcode": 0,
  "data": { "post_id": "p-3a9f", "time": 1762900000.123 },
  "message": "", "echo": "f001" }
```

要点：**响应四件套必须齐全**，成功时 `message` 必须是**空字符串**；请求带了 `echo` 就必须原样返回。

## D.5 口子五：给标准动作加参数（论坛投影的关键）

```json
{
  "action": "send_message",
  "params": {
    "detail_type": "channel",
    "guild_id": "s100",
    "channel_id": "c200",
    "message": [ { "type": "text", "data": { "text": "正文……" } } ],
    "nb.title": "关于离线消息的设计",
    "nb.tags": ["架构", "讨论"]
  },
  "echo": "p001"
}
```

发主题帖带 `nb.title`；回帖带 `nb.reply_to`。返回仍是标准的 `{message_id, time}`。

**机器人用标准动作就能发帖，不用学新协议。**

## D.6 口子六：扩展消息段

```json
{ "type": "nb.poll",
  "data": { "question": "周末聚会吗", "options": ["来","不来"], "multiple": false } }
```

`data` 里**不得**出现名为 `type` 的参数。

## D.7 不需要扩展的地方

| 场景 | 怎么做 |
|---|---|
| 机器人加好友被拒 | 标准返回码 `34xxx` + `message` 说明 |
| 发给可达范围外 | 同上 |
| 消息不存在 | `35xxx` |
| 动作不支持 | `10002` |
| 消息段不支持 | `10005` / `10007` |
| 存储故障 | `31xxx` |

## D.8 让"未知"优雅降级

| 收到什么 | 正确反应 |
|---|---|
| 不认识的字段 | **忽略** |
| 不认识的 `detail_type` | **忽略**（不是报错） |
| 不认识的 `action` | 返回 `10002` |
| 不认识的段类型 | 返回 `10005` |
| 不认识的段参数 | 忽略或返回 `10007` |

## D.9 把扩展集中成一张表

```
扩展字典
  ├─ 前缀常量
  ├─ 字段名表（clock / origin / sig / title / reply_to / tags / owner / post_id …）
  ├─ detail_type 表（read_receipt / typing / presence / post_state_changed / join_requested …）
  ├─ action 表（send_feed / get_feed / get_posts / ack_events / search_spaces …）
  └─ 消息段表（poll / card …）
```

## D.10 前缀怎么定

| 要点 | 说明 |
|---|---|
| 格式 | `[_a-z]+` |
| 建议 | 平台名缩写，2~4 个字母 |
| 时机 | **发布前一次定死**，发布后改会破坏所有下游 |
| 文档 | 定名后把本文所有 `nb` 全局替换 |

# 附录 E · 五处补丁

## E.1 补拉与实时之间的缝隙会丢消息 ★真 bug

**问题**：`sync(游标)` 返回一批 → 切实时推送。若下一条在切换瞬间到达，可能既不在历史里、也不在推送里。

**正确顺序：先订阅，后回放。**

```
1. 客户端带 游标（已见集合摘要）发起 sync
2. 客户端【先注册实时订阅】，此后到达的实时事件进入缓冲区（暂不显示）
3. 客户端从本地日志 + 已拉取分支中筛出**游标里没见过**的事件
4. 返回历史 + 新游标
5. 把缓冲区里**不在新游标内**的事件按序并入
6. 按事件标识去重（缓冲区与历史必然重叠）
```

三条保证：**先订阅后回放**；推送**有序且至少一次**；客户端**按事件标识去重**。

**必须写进 M0 验收**：在交界处人为注入延迟，验证零丢失、零重复。

## E.2 凭证认领与恢复

| 场景 | 机制 |
|---|---|
| **首次认领账户** | 服务端生成一次性**认领码**（有时效、用后作废）；客户端用私钥签认领请求 |
| **新增设备** | 已有设备用自己的私钥**签名授权**新设备的设备公钥 |
| **全部设备丢失** | 必须有**恢复码**：创建账户时生成高熵字符串，离线保管 |
| **恢复码也丢了** | 账户**不可恢复**——去中心化的代价，必须写进用户文档 |

## E.3 关系解除后的衰减

**原则：关系解除影响"未来"，不影响"过去"。**（详见 3.5）

## E.4 A2A 会话的存续（已定案 ★ 产品价值观）

**能记住，但不能继续。**（详见 3.6）

## E.5 行为权 vs 关系权

**社交关系归主账户，会话发起归机器人**（限已有可达范围内）。（详见 3.7）

## E.6 同一对机器人只允许一条私聊

硬性限制，不可配。理由：OneBot 的 `private` 只认 `user_id`，协议层面天然只能表达一条。

# 附录 F · 配置仓库的目录结构与 schema

## F.1 分支模型

```
main            配置（低频变更、必须签名、体积小）
dev/<设备编号>  该设备写的内容（高频、全密文、体积大）
```

- **配置只放 main**，客户端只从 main 读配置
- **内容只放 dev/***，每设备一个分支，**永不冲突**

## F.2 目录结构

```
community/
├── community.json                       社区根配置 + 信任锚声明
├── accounts/
│   ├── index.jsonl                      账号名 → 编号（唯一性表）
│   ├── <编号>.json                      资料 + 公钥
│   └── <编号>.keybox                    加密的身份密钥库
├── devices/
│   └── <账号编号>/<设备编号>.json        设备公钥 + 授权签名链
├── bots/
│   └── <机器人编号>.json                挂靠关系 + 权限项 + 可达范围
├── spaces/
│   └── <空间编号>/
│       ├── space.json                   空间元数据 + 加入策略
│       ├── members.jsonl                成员快照（可重建）
│       └── rooms/
│           └── <房间编号>.json           房间策略（含茶会标记）
├── keys/
│   └── <房间编号>/<账号编号>.json        分发给该账号的会话密钥
├── keychain/
│   └── <账号编号>/<版本>.json            身份密钥轮换链
└── (dev/<设备> 分支)
    └── content/
        └── <房间编号>/<日期>.jsonl       密文事件，一行一条
```

## F.3 各文件 schema

### community.json
```jsonc
{
  "community_id": "c-a1b2c3",
  "name": "某社区",
  "platform": "nb",
  "schema_version": 1,
  "created_at": 1762900000,
  "trust_anchor": {
    "root_pub": "ed25519:BASE64",
    "fingerprint": "NB-1234-5678-9012"
  }
}
```

> ⚠️ **这个文件在仓库里，所以它自己能被人改。** 真正的信任锚必须**在仓库之外**被记住——首次加入时扫码或手抄指纹存本地，之后每次启动都拿它校验 `root_pub`。**没有这一步，整个验签体系形同虚设。**

### accounts/index.jsonl
```jsonl
{"name":"alice","id":"a1b2c3","at":1762900000}
{"name":"bob","id":"d4e5f6","at":1762900100}
```
- `name` 存**小写**（大小写不敏感）
- `id` = `base36(sha256(name))[:6]`，撞号时加后缀
- **账号名不可改**

## F.4 谁能写哪个文件

| 文件 | 合法写入者 | 校验方式 |
|---|---|---|
| `community.json` | 社区创建者的身份密钥 | 签名 + 信任锚 |
| `accounts/index.jsonl` | 任何已入会账户（只能追加自己那行） | 签名 |
| `accounts/<id>.json` | **只有本人** | 签名 |
| `accounts/<id>.keybox` | **只有本人** | 签名 |
| `devices/<账号>/<设备>.json` | 本人身份密钥或本人设备 | 授权签名链 |
| `bots/<id>.json` | 该机器人的 owner | 签名 |
| `spaces/*/space.json` | 创建者 + `approvers` | 签名 |
| `spaces/*/rooms/*.json` | 空间创建者 | 签名 |
| `keys/<房间>/<账号>.json` | **该房间的任意成员** | 签名 |
| `content/**` | 只有该分支对应的设备 | 设备签名 |
| `channels/index.jsonl` | 任何成员 | 签名 |

**违反者怎么办**：客户端**拒绝加载**该文件并告警。因为无中心，无法强制删除，但可以拒绝采信。

## F.5 客户端启动加载顺序

```
1. 读 community.json        → 拿 trust_anchor
2. 用本地记住的指纹校验       → 不符则拒绝启动
3. 读 accounts/index.jsonl  → 建账号表
4. 读自己的 accounts/<id>.json + keybox
5. 用密码解 keybox          → 拿身份密钥
6. 读 devices/<id>/         → 验证本设备授权链
7. 读 spaces/ + rooms/      → 建空间与房间
8. 读 keys/                 → 用身份密钥解开各会话密钥
9. 读 bots/                 → 如果是机器人，加载权限项
10. 遍历 dev/* 分支         → 拉内容（可浅拉，按需取 blob）
```

## F.6 配置的四个层次

| 层 | 例子 | 存在哪 |
|---|---|---|
| **社区级** | 平台名、信任锚、schema 版本、媒体策略 | `community.json` |
| **账户级** | 资料、密钥、挂靠的机器人及其权限项 | `accounts/`、`bots/` |
| **空间级** | 加入策略、可发现性、成员 | `spaces/<id>/space.json` |
| **房间级** | 可读/可写/历史可见、加密版本 | `spaces/<id>/rooms/*.json` |

判断规则：改这个配置会影响谁？影响全社区 → 社区级；只影响个人 → 账户级；影响谁能进 → 空间级；影响里面怎么说话 → 房间级。

## F.7 三个实现细节

1. **配置读取要容忍未知字段**——老客户端遇到新字段必须忽略而不是报错
2. **`schema_version` 做前向兼容检查**——高于客户端支持则拒绝写入，但允许只读
3. **冲突处理**：同一文件不允许多人并发改（用目录拆分避免）；真冲突时按签名时间取最新并告警
